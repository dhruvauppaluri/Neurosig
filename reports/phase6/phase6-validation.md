# Phase 6 final engineering summary

Branch `phase5-realsignal-fixedpoint`. No SystemVerilog or FPGA file was modified. Nothing here is RTL-verified; sorter output is a comparison reference, not biological ground truth.
Detail documents: `mismatch-classification.md`, `float-vs-fixed.md`, `generalization.md`, `corrected_history/CORRECTED_PHASE3_4.md`, `../../docs/phase6-rtl-contract.md`, `../DEPRECATIONS.md`. Everything marked "reported" in Phase 5 was re-derived here, not assumed.

## Answers

**What caused the remaining 1.6 % disagreement?** First, the number: Phase 5's "98.4 %" is *exact* (timestamp, channel) agreement divided by float events (one-sided, not tolerance based). Over all 47 windows (v2): 25 184 float events, 25 146 fixed, 24 775 exact, so 98.4 % exact/float and **96.9 % Jaccard**; the baseline band gives 99.1 % / 98.4 %. Every one of the 1 526 candidate-level and 780 event-level mismatches was attributed to a first divergent stage with **0 unexplained**: crossing flips at the threshold caused by filter truncation error (443 candidates) and CAR (276), near-tied minima (380), refractory cascades (381), threshold-offset error (46), and at event level candidate cascades (629) and amplitude-error merge flips (151). The source is the specified arithmetic: truncation toward zero (RMS 0.12 µV, max 0.87 µV measured, 1.47 µV analytic worst case, deterministic +0.12 % gain that raises the integer noise estimate), *not* coefficient quantisation (zero) and *not* calibration arithmetic (unbiased). Tolerance-based agreement is higher: 24 918 of 25 184 float events have a fixed event on the same channel within 15 samples (0.5 ms); 266 do not.

**Were fixed-point implementation defects found?** Three, all specification-level slips in `fixed-v1`, fixed in `fixed-v1.1` and covered by tests that fail when each is re-introduced: the MAD→σ Q16 constant (97157 → 97164) and the clip constant (582 964 → 582 983); the shifted ADC input was not saturated to s24 (native data never reach it); a float `round` in the mean-CAR reciprocal (same values, now integer). Effect on events < 0.02 %. No defect was found in the filter, median, calibration, detector, veto or merge logic: 103 independent oracle tests (plain integers/`Fraction`, no shared code) agree bit for bit with the model, including 8 randomized whole-pipeline runs with disabled channels and dropped frames.

**What changed after correcting the historical timestamps?** Phase 3-4 compared session-clock sorter times with probe-clock samples (offset grows ~−10 µs/s, up to −31 ms). The unchanged original evaluation code with the original clock reproduces the published numbers exactly (the *control*), proving the offset explains them. Corrected: first-insertion CAR-4σ recall 0.490 → **0.682**, second insertion 0.469 → **0.480** (it was less affected: its windows are early); precision rises from ~0.4-0.47 to ~0.78 on the later first-insertion windows. The localization pilot's median axial disagreement changed from 41/80/62/42 µm to 22/20/19/23 µm (amplitude/template/beamform/robust scan); the old ranking of localization methods is deprecated. The variant ordering that led to the Phase 4 detector freeze is unchanged. Unconstrained recall contains a large chance component (e.g. 0.28-0.40 for these windows), now reported next to every number. The detector-event decode (`ibl-detector-decode.json`) mixed clocks (17-21 ms of a 200 ms window); re-run on the right timebase, within-session detector accuracy moved 0.2 → 0.4 and cross-recording 0.7 → 0.3 with only 5 and 10 test trials, i.e. noise: no decoding conclusion either way.

On the locked set: baseline F1 0.487 [0.447, 0.517], v2 0.498 [0.455, 0.528] (chance 0.17); recall 0.444 → 0.448, precision 0.539 → 0.560, false detections/s ×0.93. At 0.5 ms ΔF1 = +0.016 [+0.010, +0.023], at 2 ms +0.008 [+0.002, +0.014]. Per channel (70 channels with ≥ 20 reference spikes) v2 recall ≥ baseline on 45. **Negative result:** session F (lowest noise, 6.1 µV; lowest sorter rate, 148 spikes/s; low overall agreement, F1 0.33) is worse with v2 in 4 of 6 windows (recall 0.362 → 0.333). The cause was not tested (a hypothesis is reduced sensitivity to narrow, fast spikes with the narrower band); with one such session of four, universal improvement is not claimed. Overall the gain is real but small (~+0.01 to +0.02 F1), shrinks from development to locked data as expected, and is mainly precision, not recall. Mean CAR in place of median is **not** a free simplification: locked ΔF1 vs median −0.011 [−0.019, −0.002] (sessions: E −.015, F +.010, G −.018, H −.021), recall −5 points, false detections/s −32 %; the sign depends on the session.

**Does fixed-point processing preserve detection quality?** Yes, to within measurement noise. Against the sorter (channel-consistent F1 at 1 ms, chance-adjusted): all 47 windows float 0.5283 vs fixed 0.5279 (difference −0.0004 [−0.0009, +0.0002]; chance F1 0.184 both); locked windows float 0.4978 vs fixed 0.4976 (−0.0003 [−0.0011, +0.0007]); baseline band −0.0002 [−0.0007, +0.0002]. On the locked windows 11 316 of 11 504 float events are reproduced exactly (98.4 %; Jaccard 96.8 %). This is evidence that quantisation does not change agreement with the sorter, not that either detector is biologically correct.

**Is the fixed-point reference ready to serve as the RTL golden model?** As a software contract, yes: integer-only, deterministic, fully specified (widths, signedness, rounding, truncation, saturation, reset, gaps, end of stream), verified by two independent implementations plus an independent oracle, with 116 committed vector files including every intermediate stage (filter sections, reference, CAR output, calibration registers, candidates, post-veto, events) and unit vectors per block. Not specified: timestamp wrap (39.8 h), event-queue depth, cycle timing. It has not been checked against any RTL, and the intended calibration (offline, on the evaluated window) has been tested on another window of the same session only once (Phase 5, same F1).

**Which modules would need modification in the later RTL phase?** From `docs/phase6-rtl-contract.md`: `spike_band_filter` (30 kHz 200/4500 Hz coefficients as parameters, 10-bit guard shift, s24 input saturation); **new** frame assembler and CAR stage (median selector, `sat24` subtract); `spike_detector_channel` (armed bit, per-channel baseline/threshold/reciprocal registers, `delta` and `amp_q8` outputs, valid/active handling, 15/30-sample windows); **new** artifact-veto block; `spike_event_merge` (key `amp_q8`, tie rule timestamp then channel, `(timestamp, channel)` ordering); `neurosig_pipeline` (frame synchronisation, per-frame valid/active, calibration register file, end-of-stream flush); event output record (`timestamp, channel, code, delta, amp_q8`).

**What remains scientifically uncertain?** Whether the narrower band helps outside these eight sessions (one of four locked sessions got worse and the reason is unknown); how much of the sorter's disagreement is missed biology versus sorter misses (sorter excludes low-amplitude units); what the +0.12 % gain and truncation noise do to very small signals in other probes; on-chip calibration (offline calibration only was tested); the remaining 3-4σ sub-threshold fraction (~20 % of reference spikes) which no tested change recovered; behaviour with non-10-bit ADCs; any hardware cost (no synthesis, timing, area or power exist). Matching uses two circular shifts for the chance level; intervals are window-cluster bootstraps with 24-48 windows.

## Protocol and what was and was not re-checked
* Locked set: 4 new insertions (hausserlab `c5b9e063`, angelakilab `5135e93f`, steinmetzlab `18d316bf`, UCLA `730770d6`), 6 seeded 2 s windows each, reserved in `split_manifest_phase6.json` before any download or evaluation; the only change after drawing was replacing a mainenlab insertion that has no raw AP files (before any window was fetched). Frozen configurations (`reports/phase5/detector-v2.json`) and the manifest hash are recorded in `generalization.json`; the evaluation is deterministic (a later rerun to add legacy windows reproduced the locked numbers exactly), and no parameter was changed after viewing them. Phase 5's held-out windows are reported as a previously used benchmark.
* Time-base correction was kept separate from detector parameters: no detector parameter changed in `corrected_history`.
* Regression: `scripts/run_regression.py` → 229 passed, 0 failed, 0 skipped (with cached windows); in a clean minimal environment without data 225 passed and 4 real-data checks reported `missing_dataset` (not as passes). The software-only workflow `.github/workflows/software-tests.yml` runs the same suite without data downloads or FPGA.

## Limitations and recommended next milestones
1. **Run the SystemVerilog implementation phase against the vectors** (filter → frame assembler/CAR → calibration registers → detector → veto → merge), comparing stage by stage; keep Python as the oracle.
2. **Investigate session F** (spike width/amplitude, sorter unit mix, per-channel recall) before deciding whether 200-4500 Hz should be the shipped band; consider a band chosen per probe at calibration time.
3. **More independent recordings**: the data server was intermittently refusing downloads (HTTP 403) during this phase; extend the locked set to more labs and a non-VIS region.
4. **On-chip calibration study**: streaming median/MAD or histogram estimators versus offline registers, evaluated with the same chance-adjusted metrics.
5. **Decide median vs mean CAR deliberately** with hardware cost numbers from synthesis, since the detection trade-off is session dependent.
6. **Synthesis/PPA exploration** only after the RTL matches the vectors exactly.
7. Re-evaluate the detector-to-trial decode with a much larger trial count (the corrected 10-11 trial rerun is uninformative).
